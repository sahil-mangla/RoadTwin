## Phase Goal

**As a** RoadTwin operator running the dev stack, **I want to** submit a road report from a browser page and immediately see it listed back with its GPS accuracy and `unverified` status, **so that** the seven-entity data contract every later intelligence phase depends on is proven real and wired before any intelligence code is written.

<objective>
Make the *whole* seven-entity contract observable, not just Report: a chain-seed endpoint that writes one linked row into each of the seven tables, a schema-status endpoint that reports live per-entity row counts, a status-transition endpoint that exercises the lifecycle, and the browser panel that surfaces all three.

This is what turns ROADMAP Phase 1's four success criteria from assertions in a test file into something a human can watch happen.

Purpose: SCHM-01 (seven distinct, *related* entities, proven by a single linked insert), SCHM-02 (append-only proven by seeding twice and watching counts grow), SCHM-03 (the lifecycle actually transitions, and new rows always arrive `unverified`).
Output: Chain/status/transition endpoints, the two remaining `01-VALIDATION.md` test files, and the schema-status panel.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/skeleton/chain` | An unauthenticated call now writes seven rows per invocation. |
| browser → `PATCH /api/skeleton/reports/{id}/status` | A client can move a report's lifecycle state. |
| browser → `GET /api/skeleton/schema-status` | Row counts are disclosed to any caller. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-13 | Elevation of Privilege | `PATCH /api/skeleton/reports/{id}/status` | medium | mitigate | The endpoint lives on the skeleton router, mounted only when `settings.skeleton_routes_enabled`, and is covered by the retirement criteria in `01-SKELETON.md`. Its docstring records that real transition-validity rules belong to Phase 5 and that authenticated, role-gated status changes are AUTH-02 / RPWF-01 in Phase 7. The payload accepts only the four `ReportStatus` enum values; anything else is a 422. |
| T-01-07 | Denial of Service | unauthenticated chain seeding writing seven rows per call | low | mitigate | Router remains gated behind `settings.skeleton_routes_enabled` with a startup warning; CORS stays restricted to the two localhost Vite origins; nothing is deployed this phase. Rate limiting is INGT-03 in Phase 2. |
| T-01-14 | Information Disclosure | `GET /api/skeleton/schema-status` row counts | low | accept | Row counts of a local development database carry no sensitive content, and the route is gated behind the same skeleton flag. Accepted rather than mitigated because the diagnostic value in this phase outweighs a disclosure with no confidential payload. |
| T-01-03 | Tampering | count queries in the new endpoints | high | mitigate | Counts are built with SQLAlchemy `select(func.count())` constructs against mapped tables; no value is interpolated into query text. Re-gated by the interpolated-SQL grep in Task 1's acceptance criteria. |
| T-01-06 | Repudiation | append-only accumulation across repeated seeds | medium | mitigate | The chain seed writes the three time-series entities exclusively through their append-only repositories, and both the automated double-seed growth check and the human-check confirm counts increase rather than reset (SCHM-02, D-08). |
| T-01-10 | Information Disclosure | rendering server-returned entity names and text | low | mitigate | All values render as React children (auto-escaped); no raw-HTML injection API is used anywhere under `frontend/src/`. |
</threat_model>
